# Review Reference

Single source for `deep-review`: the dimension matrix (candidate rows + the "what must be proven" statement), fix routing, and fix metrics. Column semantics are defined in `SKILL.md` `## Scope`; `scripts/verify-matrix.ts` proves the invariants after any edit.

## Dimension Matrix

Seeds `### 1. Think` and is the row contract every later step reads — `/deep-thinking` + review CLI/linter output decide applicability (never a blind sweep). One row per dimension.

- `Check` is the proof statement for `### 3. Fan out`. A `capture` row runs its `Tool/skill` first and dispatches the reviewer with that output; a `manual` row dispatches with the row + the files named in evidence; the parent absorbs a row only under the ≤ 2-findings rule.
- The only legal `skipped` reason is the row's `N/A condition`, quoted as the ledger reason — never "there probably isn't a problem".
- `Default severity` is the value when no trigger applies; moving off it needs the cited upgrade trigger.
- Tool missing on the machine → `/download-program`; unavailable on the platform (e.g. Lightpanda on Windows — see `use-lightpanda`) → ledger `failed (tool-unavailable)`, never `skipped`.
- The proof statement must stay checkable by a reviewer with no codebase context — if the named files or captured output cannot answer it, it is too vague to dispatch.

### Matrix Notes

- Invariants — run `bun scripts/verify-matrix.ts` from this skill's folder after any edit (exits non-zero, one line per violation): every `Tier`/`Impact`/`Cost`/`Fix mode`/`Evidence`/`Enforcement`/`Gate` value is in its vocabulary; `Evidence` contains `cli` ⇒ `CLI domain` ≠ `—`; `Enforcement: cli-check` ⇒ `CLI domain` ≠ `—`; `Cost: high` ⇒ `Gate` ≠ `pr`; `Fix mode: codemod` ⇒ `Enforcement` is `ast-grep`/`cli-check`; no alias equals a row name; every `Fix owner` exists in an `improve`/`optimize` scope-map or a `## Domain Map` route; every scope-map label resolves to a row (name or `Aliases`).
- Adding a row = this table row + a scope-map label + a `Fix owner` that already exists; prefer extending an existing row when trigger, authority, and owner are not all distinct. A row whose `Tool/skill` exists on no machine lands in the ledger as `failed`/`manual` every run.
- Alias resolution: a `review-<label>` is answered by every row whose `Aliases` cell lists it or whose name equals it, plus the `always` tier — read that set from the table, never re-resolve by hand; `review-issues`/`review-gaps` are exempt (they hold their own work). A label on no row is a matrix gap — report it, never invent a dimension.
- Rows sharing a fix owner are still dispatched as separate ledger dimensions — the owner matters only at `### 6. Route`.
- `CLI domain` = the `wrikka-linter` pack owning the row's rules (`quality`/`security`/`structure`/`config`/`deps`, from the rule-id prefix); `—` = no pack, so the row has no slice and takes the `capture`/`manual` route. A durable analyzer gap is only a `cli-check` row whose rule never fires (`### 3` step 6).
- Raw CLIs named in a row's `Tool/skill` (`promptfoo`, `trufflehog`, `garak`, `ragas`, `git-sizer`, …) are run directly — install with `/download-program`, use the invocation the row names (`promptfoo eval`, `trufflehog --only-verified`), and when a row gives no flags read the tool's `--help` via `/learn-from-cli` instead of guessing. Do not create a `follow-tool-*` wrapper for them; a wrapper is written only when the user asks for one. Authority pins are current as of 2026-10 — re-verify via `/deep-research` when one looks stale.

### Label resolution

The `improve`/`optimize` scope-maps name review targets as `review-<label>` — each is answered by every matrix row whose `Aliases` cell lists it or whose row name equals it (a label may map to several rows, e.g. `frontend` → `routing-deeplinks`, `rendering-strategy`, `uxui`, `form`), plus the `always` tier; read that set from the table and hand it to `/deep-review`, never re-resolve by hand. `review-issues`/`review-gaps` are exempt. A label found on no row is a matrix gap — dispatch the `always` tier plus the closest artifact-match rows and report the gap, never invent a dimension; `scripts/verify-matrix.ts` proves every scope-map label resolves.

### Fix boilerplate

1. Rank findings by severity — critical first, then fix one at a time with verification immediately after each fix
2. Pick the fix route matching each finding from the lookup order above
3. Every fix preserves existing behavior, passes `/run-check` and `/run-test` if present, then summarizes with `/report-before-after`

## Fix Metrics

Scored after `### 7. Fix` runs (no fix step → no metric).

Fix score = fixes verified / fixes attempted × 100 — grade A (90+), B (80+), C (70+), D (60+), F (<60)

| No. | Metric | Description | How To Calculate |
|-----|--------|-------------|------------------|
| 1 | Review Coverage Ratio | % reviewed items in scope that were fixed and verified | fixed / total × 100 |
| 2 | Reverted-Fix Rate | % fixes reverted or not accepted (not the analyzer's finding-level `falsePositiveRate`) | reverted fixes / total fixes × 100 |
| 3 | Evidence Strength Score | % findings with evidence (file/line) | findings with evidence / total findings × 100 |
| 4 | Actionability Score | % findings with a clear recommendation | actionable findings / total findings × 100 |
| 5 | Severity Distribution | count of findings per severity | count of Critical/High/Medium/Low/Info |
| 6 | MTTR Estimate | estimated time to fix and verify | Critical=1d, High=3d, Medium=7d, Low=14d average |
| 7 | Before/After Trend | score improvement over time | (after - before) / before × 100 |
| 8 | Risk Exposure Index | high-severity unfixed issues in critical areas | count of Critical/High findings in critical scope |
| 9 | Scope Boundary Adherence | % fixed issues inside the declared scope | in-scope findings / total findings × 100 |
| 10 | Documentation/Report Quality | % fixes with file/line and reason | documented findings / total × 100 |
| 11 | Accepted-Finding Rate | % findings accepted instead of fixed — each must carry a linked issue + expiry | accepted with issue+expiry / total findings × 100 |

Domain-specific: Fix Success Rate (fixes verified / total fixes × 100), Regression Rate After Fix (regressions / total fixed × 100), Verification Coverage (verified findings / total findings × 100).
