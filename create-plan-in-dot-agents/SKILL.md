## Goal

Analyze the problem/context deeply and produce a readable, implementation-ready plan with scoring and progress tracking — canonical for plan persistence: the plan content is generated by `/deep-plan`, then created as a GitHub issue (label `plan`, body = full plan with `- [ ]` task checklist) so it survives sessions and machines; only when the repo has no GitHub remote (or `gh` is unauthenticated) → fall back to `.devin/temp/plan/<workspace>/<title-date>.md`

## Scope

- Takes a request or topic — use for all kinds of planning: new features, refactors, migrations, multi-item work
- Plan content (think → analyze → research → score → order) is generated by `/deep-plan` — this skill owns only the plan template and persistence
- Default: persist as a GitHub issue — repo has a GitHub remote and `gh` is authenticated (checked in Step 1); no remote / `gh` unusable / `file-only` argument → fall back to a plan file; `chat-only` → run `/deep-plan` and report in chat, skipping Steps 3-5 (nothing created)
- Every task specifies File/What/How/Deps/Acceptance/Risk in full — the plan must be implementable without further questions
- Official resources: https://devin.ai , https://docs.devin.ai

## Execute

### 1. Capture And Prepare

> Goal: Gather context and decide the persistence target (GitHub issue vs fallback file)

1. Take `<topic>` from the argument or the current session's context
2. Read the relevant context, design, and reports; if the scope is ambiguous → run `/ask-me`
3. Confirm the target workspace with the user if it is not clear
4. Determine `<workspace>` = the directory name of the target workspace
5. Detect the persistence target: `gh repo view --json nameWithOwner` (has remote + authenticated → issue; otherwise → file). No remote → run `/create-github-repo` first when the user wants durable tracking, else fall back
6. File-fallback path only: check `.devin/temp/plan/<workspace>/` exists (create if missing) and run `/update-gitignore` if `.devin/temp` is not yet ignored

### 2. Generate Plan Content

> Goal: a decision-complete, scored plan body from the deep orchestrator — no guessing here

1. Run `/deep-plan <topic>` — it performs `/deep-thinking` → `/deep-analyze` (file:line evidence) → `/deep-research` (deps/patterns) → feature scoring → ordering + quality gates, and executor-standard checks (`/refactor`, `/implement-to-production`, TDD loop)
2. Take the returned plan content: features + scores, file changes, task graph, risks, test strategy, assumptions, acceptance criteria, execution order
3. If `/deep-plan` returns open unknowns that block writing → run `/ask-me` before continuing

### 3. Check For Duplicate

> Goal: Avoid writing duplicate plans

1. Issue target: `gh issue list --label plan --state open --search "<topic keywords>"` — an open plan issue for the same topic → update its body (edit) or add a revision comment instead of creating a new one
2. File target: search `.devin/temp/plan/<workspace>/` for files whose names resemble the current `<topic>` — update the original or create a new revision based on context
3. Record the chosen title — issue form `<type>: <short title>`; file form `<short-kebab-title>-<YYYY-MM-DD>.md`

### 4. Build Plan Body

> Goal: Assemble the plan content with all sections — column conventions in `## Plan Template`

1. Write `## Goal` — summarize the desired outcome in 1-3 lines
2. Write `## Architecture` — an ANSI diagram or references to the relevant architecture; use `/report-architecture-diagram` if a new drawing is needed
3. Write `## Idea Features` — features + scoring table from `/deep-plan` output, formatted per the Features row of `## Plan Template`
4. Write `## File Changes` — the `No. | File | Action | What | How | Acceptance | Risk` table from `/deep-plan` output
5. Write `## TODO` — tasks table tracked with a `Status` column
6. Write `## Task Graph` — dependencies between tasks + critical path
7. Write `## Risks` — table of risk, impact, mitigation
8. Write `## Test Strategy` — required coverage, fixtures, regression
9. Write `## Assumptions And Unknowns` — what was assumed and the open questions
10. Write `## Acceptance Criteria` — checkbox list
11. Write `## Execution Order` — numbered list ordered by critical path

### 5. Persist And Open

> Goal: Create the durable plan (GitHub issue by default, file on fallback) and hand off

1. Issue target (default): create via `/create-github-issue` — title from Step 3, body = full plan (Step 4), label `plan` (create the label once if missing), assignee = self; fall back to `gh issue create --title ... --body-file <temp-md> --label plan --assignee @me`
2. File target (fallback: no remote, `gh` unauthenticated, or `file-only`): write `.devin/temp/plan/<workspace>/<title>-<YYYY-MM-DD>.md` and open it in the editor
3. Tell the user the issue URL (or file location) and summarize the plan
4. Recommend `/implement-to-production` as the next step — reference the issue number in the branch/PR body (`Fixes #<n>` closes the plan issue when done)
5. Progress tracking: tick the `## TODO`/acceptance `- [ ]` checkboxes in the issue body as tasks complete (`gh issue edit` / via `/create-github-issue` edit flow) — never fork status into a second place
6. Use `/suggest-next-action` if the next action is unclear

## Plan Template

Column conventions for the tables written in Step 4 — the plan must be easy to scan and trackable by `/implement-to-production`:

- Features (`## Idea Features`): `Icon | No. | Feature | Description | Files Change | Impact | Risk | Effect | Score | Phase` — `Icon` always first (Iconify CDN URL, `?color=%23hex` query to signal levels); `Score` from `/deep-plan` `## Rules → 1. Scoring`; add a `Dependencies` column when features depend on each other
- File Changes (`## File Changes`): `No. | File | Action | What | How | Acceptance | Risk` — `Action` = `create`/`update`/`delete`/`rename` matching the actual work; `What` lists the API signatures/types to add or change; `How` references the pattern/abstraction reused from the codebase; every row needs evidence from deep-analyze — never guess paths
- TODO (`## TODO`): `No. | Task | Status | Depends On | Expected Outcome` — `Status` = `pending`/`in-progress`/`completed` matching what `/implement-to-production` reads; `Expected Outcome` measurable
- Task Graph (`## Task Graph`) — dependencies by task `No.` (e.g. `1 → 2, 3 → 4`), the longest critical path, and tasks that can run in parallel; a depended-on task always comes first
- Risks (`## Risks`): `Risk | Impact | Likelihood | Mitigation | Rollback` — `Mitigation` is a concrete action, not a broad description; `Rollback` states how to revert if the risk occurs
- Test Strategy (`## Test Strategy`) — coverage target required after implementation, fixtures/test data to prepare, regression tests to add or update, the actual test file paths from the codebase
- Assumptions And Unknowns (`## Assumptions And Unknowns`) — assumptions with reasons; open questions that require `/ask-me` before implementing; never leave unknowns empty when there is risk — ask before writing the plan
- Acceptance Criteria (`## Acceptance Criteria`) — `- [ ]` checkboxes, one per criterion, focused on observable results, required action stated clearly
- Execution Order (`## Execution Order`) — numbered list of task `No.` ordered along the critical path; note parallelizable tasks if any

## Rules

### 1. Plan Quality

- Every task must fully specify: `File` (path + action), `What` (API signature/types), `How` (pattern), `Deps` (existing/new + version + publish age), `Why` (+ rejected alternatives), `Acceptance` (measurable), `Risk` (impact + rollback)
- Never use placeholders, `TBD`, `TODO`, or steps that cannot be implemented — the plan must be executable without further questions
- Every claim needs evidence from Step 2 (file:line) — never guess APIs or paths
- Tasks must be written so `/implement-to-production` can execute them as-is (and `/refactor` when the task is structural) — read both before planning, never plan work that contradicts their rules
- Reuse first: a pattern repeated ≥3 places → add an extraction task; a migration with shared code → order shared → consumers → delete dead
- A new dependency must be version-pinned + published ≥7 days + with the reason for choosing it

### 2. Plan UX

- The plan body is one markdown document that renders on both targets: the GitHub issue body and the fallback file use the same `## Plan Template` conventions — keep tables GitHub-issue-compatible (plain pipe tables, no HTML-wrap needed for cells)
- Visual hierarchy: `##` for main sections, `###` for subsections, never skip heading levels; `>` only for short highlights
- Use tables with English Title Case headers for comparison; keep cell data short (≤1-2 lines); plain alignment; avoid overly wide tables
- Icons: Iconify CDN icons in the `Icon` column and headings; color query `?color=%23hex` signals levels (green = Low risk, red = High); avoid emoji unless necessary; never rely on color alone — pair icons with text labels
- Do not use bold markers `**` in the body — use headings/bullets instead
- Center ANSI diagrams with `<div align="center">`; every line in an ANSI codeblock must have equal length; use ` ```text ` codeblocks for diagrams; no images without real evidence
- No separate `## Information`, `## Key Concepts`, or `## Tech Stack` sections

### 3. Scoring

- Scoring formula and scale are owned by `/deep-plan` `## Rules → 1. Scoring` — never restate or invent a formula here (SSOT: `/follow-single-of-source`)
- Show the scale and the formula in the plan body; every row of the features table must have a real score
- Every feature must have `Icon` as the first column

### 4. Persistence Safety

- Issue target: create/edit only the plan issue this skill owns — never close, delete, or overwrite an unrelated issue without confirmation; keep progress edits scoped to the `## TODO`/acceptance checkboxes (see Step 5.5)
- File fallback: write only inside `.devin/temp/plan/<workspace>/` — never touch source code; `.devin/temp` must be in `.gitignore` before creating files — if not, run `/update-gitignore`
- Idempotent: re-running must not accidentally create a duplicate plan issue or plan file (see Step 3)
- `chat-only` mode: if the caller specifies it clearly → run `/deep-plan` and report in chat, skip Steps 3-5, create nothing (no issue, no file, no `.devin/temp`)
- Never delete or close old plans without confirmation — keep them as history (issue: leave closed with a reference; file: keep)

### 5. Split Scope

- `/deep-plan` is the independent generator of plan content (think → analyze → research → score → order); this skill is the sole owner of plan persistence — GitHub issue by default, `.devin/temp/plan/` file on fallback
- `/plan` is the alias stub that forwards to this skill
- Callers wanting chat-only planning use `/deep-plan` directly; planning work that must persist goes through this skill only — never create plan files outside `.devin/temp/plan/` and never create plan issues without the `plan` label

## Expected Outcome

- An implementation-ready plan complete with features, scoring, File Changes, TODO, Task Graph, Risks, Test Strategy, and Acceptance Criteria
- The plan is durable: a GitHub issue with label `plan` (URL reported, `- [ ]` checkboxes trackable via `gh issue edit`) — or the fallback file at `.devin/temp/plan/<workspace>/<title>-<YYYY-MM-DD>.md`, opened in the editor with `.devin/temp` ignored in `.gitignore`
- No placeholders — every task has evidence, dependencies, and measurable acceptance
- Ready to hand off to `/implement-to-production` with `Fixes #<n>` tracking and tasks already aligned to `/refactor` and the TDD loop
