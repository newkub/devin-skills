## Goal

ติดตามไฟล์คิวงานและรันงานที่ค้างอยู่อัตโนมัติเมื่อตรวจพบการเปลี่ยนแปลง

## Scope

ใช้กับ workspace ที่มีคิวงานหรือ `QUEUE.md` ที่ต้องทำงานต่อเนื่อง ครอบคลุมการอ่านคิว ติดตามการเปลี่ยนแปลง รันงาน และรายงานผล ไม่ใช่การสร้างคิวงานใหม่ (สร้าง `QUEUE.md` ด้วย `write`) และไม่ใช่การรันงานครั้งเดียว (ใช้ `/run-task-all`)

## Execute

### 1. Read Task Queue

อ่านคิวงานและระบุงานที่ค้างอยู่ก่อนเริ่ม watcher

> Goal: ทราบงานที่ค้างอยู่และลำดับ priority ก่อนเฝ้าติดตาม

1. อ่าน `QUEUE.md` หรือไฟล์คิวงานที่ตรวจพบใน workspace
2. ระบุงานที่มีสถานะ pending หรือยังไม่สมบูรณ์
3. เรียงงานตาม priority และ dependency ที่ระบุในคิว
4. บันทึกรายการงานเริ่มต้นเป็น baseline เพื่อเปรียบเทียบการเปลี่ยนแปลงภายหลัง
5. ถ้าไม่พบไฟล์คิว → stop และ report ว่าไม่มีงานให้ติดตาม

### 2. Watch For Changes

เฝ้าไฟล์คิวงานเพื่อตรวจจับงานใหม่หรืองานที่แก้ไข

> Goal: ตรวจจับการเปลี่ยนแปลงของคิวงานอย่างต่อเนื่องและไม่ซ้ำซ้อน

1. เฝ้าไฟล์คิวงานด้วย native file watcher หรือ polling ตาม environment ที่ตรวจพบ
2. ตรวจจับงานใหม่ งานที่แก้ไข หรือการเปลี่ยนแปลงสถานะใน `QUEUE.md`
3. debounce การเปลี่ยนแปลงที่เกิดขึ้นติดต่อกันเร็วเกินไป เพื่อไม่ให้ trigger ซ้ำ
4. รักษา watcher instance เดียวต่อไฟล์คิวเพื่อหลีกเลี่ยง duplicate triggers
5. ถ้า watcher ไม่พร้อมใช้งาน → fallback เป็น polling ทุก 5 วินาทีและ report ให้ผู้ใช้ทราบ

### 3. Run Pending Tasks

รันงานที่ค้างอยู่ตามลำดับเมื่อตรวจพบการเปลี่ยนแปลง

> Goal: รันงานที่ค้างอยู่อัตโนมัติตามลำดับและหยุดเมื่อเกิด error

1. เรียก `/run-task-all` สำหรับรันงานทั่วไป หรือ `/deep-plan` สำหรับงานที่ต้องการวางแผนก่อน
2. รันงานตามลำดับ priority และ dependency ที่ระบุในคิว
3. บันทึกผลลัพธ์ของแต่ละงานว่าสำเร็จหรือล้มเหลว
4. ถ้าเกิด error → ลองใหม่สูงสุด `5` ครั้งก่อนหยุดและ report
5. ถ้างานเป็น destructive action → หยุดและถามผู้ใช้ก่อนดำเนินการ
6. หยุดการรันเมื่อเกิด error ที่ไม่สามารถ retry ได้และ report สถานะ

### 4. Update Status

อัปเดตสถานะงานในไฟล์คิวหลังรันเสร็จ

> Goal: สถานะในไฟล์คิวเป็นปัจจุบันและสอดคล้องกับผลการรัน

1. อัปเดตสถานะงานที่รันเสร็จเป็น done หรือ failed ใน `QUEUE.md`
2. บันทึก error message สำหรับงานที่ล้มเหลวเพื่อให้ตรวจสอบได้ภายหลัง
3. ถ้างานมี dependency → ตรวจว่างานที่ dependent ยังสามารถรันได้หรือต้องหยุด
4. ถ้าการอัปเดตสถานะซ้ำกับที่มีอยู่ → ข้ามเพื่อหลีกเลี่ยง side effect ซ้ำ

### 5. Report

รายงานผลและแนะนำ action ถัดไป

> Goal: ผู้ใช้ทราบงานที่เสร็จ ล้มเหลว และขั้นตอนถัดไป

1. บันทึกงานที่เสร็จและล้มเหลวพร้อมจำนวน retry
2. สรุปสถานะคิวงานปัจจุบันเป็น bullet points สั้นๆ
3. แนะนำ action ถัดไป เช่น แก้งานที่ล้มเหลวหรือเพิ่มงานใหม่
4. ทำ `/suggest-next-action` เพื่อแนะนำขั้นตอนถัดไป

## Rules

### 1. Safety

- ห้ามรันงานที่ทำลายล้างโดยไม่ได้รับการยืนยันจากผู้ใช้
- ถ้างานมีคำสั่งลบ ย้าย หรือ overwrite → หยุดและถามผู้ใช้ก่อนดำเนินการ

### 2. Watcher Management

- ใช้ polling หรือ native file watcher ตาม environment ที่ตรวจพบ
- มี watcher instance เดียวต่อไฟล์คิวเพื่อหลีกเลี่ยง duplicate triggers
- debounce การเปลี่ยนแปลงที่เร็วติดต่อกันเพื่อไม่ให้ trigger ซ้ำ

### 3. Retry And Error Handling

- ลองใหม่งานที่ล้มเหลวสูงสุด `5` ครั้งก่อนหยุด
- บันทึก error message ของงานที่ล้มเหลวเพื่อให้ตรวจสอบได้
- ถ้า error ไม่สามารถ retry ได้ → stop และ report ทันที

### 4. Deterministic Execution

- รันซ้ำด้วย input เดิมต้องได้ผลลัพธ์เดิม ไม่สร้าง side effects ซ้ำ
- ถ้าการอัปเดตสถานะซ้ำกับที่มีอยู่ → ข้ามเพื่อหลีกเลี่ยงการเขียนซ้ำ

### 5. Graceful Shutdown

- หยุดทันทีเมื่อ user กด `Ctrl+C`
- บันทึกสถานะงานที่กำลังทำอยู่ก่อนหยุด
- ปิด file watcher อย่างสะอาด

### 6. Rollback Safety

- ก่อนรันงานที่เสี่ยงสูง ให้บันทึกสถานะ `QUEUE.md` ก่อน
- ถ้างานล้มเหลวและทำให้ state เสีย → คืนค่า `QUEUE.md` จากสำเนา

## Expected Outcome

- คิวงานถูกติดตามอย่างต่อเนื่องโดย watcher หรือ polling
- งานที่ค้างอยู่ถูกรันอัตโนมัติตามลำดับ priority
- สถานะใน `QUEUE.md` เป็นปัจจุบันและสอดคล้องกับผลการรัน
- งานที่ล้มเหลวมี error message บันทึกไว้เพื่อตรวจสอบ
- ผู้ใช้ทราบสถานะคิวและ action ถัดไปที่ควรทำ
